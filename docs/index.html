Enterprise Appliance Deployment Guide

DataStrat AI Production Documentation

Deploy, configure, and operate DataStrat AI inside your sovereign enterprise VPC. This guide is written for client IT, Security, and DevOps teams running production workloads.

Docker Compose v2 Dual-Subdomain OIDC (Zitadel) Hybrid Local or Managed Cloud Storage Zero Cloud Telemetry

Product Overview & Capabilities

DataStrat AI is a self-contained enterprise AI appliance built to automate and streamline DCAM (Data Management Capability Assessment Model) evaluations. Combining Retrieval-Augmented Generation (RAG) with LangGraph agentic reasoning, the platform conducts structured interviews, evaluates governance artifacts, and recommends maturity scores within your private infrastructure.

Agentic DCAM Interviews LangGraph

Conversational assessment agent that adapts follow-up questions to stakeholder responses and validates evidence against DCAM standards.

Evidence Saturation RAG + Qdrant

Real-time ingestion and semantic indexing of uploaded governance documents with visual completeness tracking.

Role-Based Governance OIDC RBAC

Built-in Auditor and Compliance Officer separation so AI maturity suggestions are reviewed and finalized by human officers.

Hybrid VPC Ready Stateless

Run completely self-contained with bundled containers or connect directly to managed RDS, Redis, Qdrant, and S3 services.

System Architecture

DataStrat AI uses a decoupled microservice topology segmented across three isolated Docker bridge networks (frontend_net, backend_net, and db_net). All external traffic enters through a single Nginx reverse proxy using a dual-subdomain routing model so authentication and application traffic traverse standard HTTPS/HTTP ports (443 / 80).

Production Container Services

Prerequisites & Hardware/VM Requirements

Host & Software Requirements

  • Operating System: 64-bit Linux VM (Ubuntu 22.04/24.04 LTS, Debian 12, or RHEL 9+).
  • Container Runtime: Docker Engine 24+ and Docker Compose v2 (docker compose plugin).
  • Host Utilities: openssl, unzip, curl or wget, and rsync (recommended for seamless upgrades).
  • Container Registry Access: GitHub Personal Access Token (PAT) with read:packages scope to pull images from ghcr.io.

VM Sizing & Worker Concurrency

Document ingestion is memory-intensive. Configure CELERY_CONCURRENCY and CELERY_MAX_TASKS_PER_CHILD during setup based on available host RAM:

Recommended VM Sizing Tiers
Deployment Tier vCPU RAM Disk (SSD) Recommended Celery Settings
Standard Production 4–8 vCPU 8–16 GB 50–100 GB CELERY_CONCURRENCY=2, CELERY_MAX_TASKS_PER_CHILD=10
High-Throughput Production 8+ vCPU 32+ GB 100+ GB CELERY_CONCURRENCY=4 (or higher), CELERY_MAX_TASKS_PER_CHILD=10
Constrained Evaluation VM 2–4 vCPU ≤ 4 GB 30 GB CELERY_CONCURRENCY=1, CELERY_MAX_TASKS_PER_CHILD=1 (prevents OOMs)

DNS & Firewall Matrix

Before running the deployment wizard, create two DNS A records pointing to your VM or Load Balancer IP:

  • Application Domain: e.g., app.datastrat.example.com (serves UI, API, and /grafana/).
  • Authentication Domain: e.g., auth.datastrat.example.com (serves Zitadel OIDC endpoints).
Firewall & Port Exposure

Application services (api, ui, postgres, redis, qdrant, minio) bind to 127.0.0.1 by default via HOST_BIND_IP. Only nginx exposes public ports 80 and 443 (plus 8080 for optional local fallback). Ensure outbound HTTPS (443) is permitted to ghcr.io, github.com, and your LLM provider endpoint.

Production Deployment Guide

Step 1: Authenticate to the Container Registry

Log in to GitHub Container Registry using a PAT with read:packages permission:

bash
echo "YOUR_GITHUB_PAT" | docker login ghcr.io -u YOUR_GITHUB_USERNAME --password-stdin

Step 2: Download & Extract the Release Package

Fetch the official enterprise deployment archive from DataStrat-AI/datastrat_ai_release:

bash
wget https://github.com/DataStrat-AI/datastrat_ai_release/releases/latest/download/datastrat-enterprise-deployment.zip
sudo apt-get update && sudo apt-get install -y unzip
unzip datastrat-enterprise-deployment.zip -d datastrat-deploy
cd datastrat-deploy

Step 3: Run the Interactive Deployment Wizard (./deploy.sh)

The deploy.sh script initializes .env from .env.example, generates cryptographic secrets, configures Nginx SSL/headers, and locks permissions with chmod 600 .env.

bash
chmod +x deploy.sh update.sh
./deploy.sh

During the wizard, you will select:

  1. Infrastructure Mode: Built-in local storage containers (COMPOSE_PROFILES=local-storage) or External Managed VPC services (RDS, ElastiCache, Qdrant Cloud, S3).
  2. Domains: Your app_domain and auth_domain.
  3. SSL / HTTPS Mode:
    • Option 1 — External Load Balancer (Recommended for Cloud): Cloudflare, AWS ALB, or Azure Application Gateway terminates TLS. Nginx maps $pref_proto to https and sets AUTH_TLS_MODE=external.
    • Option 2 — Local Machine SSL (Nginx): Nginx terminates TLS on port 443 using either a generated self-signed cert in ./certs/ or your enterprise .crt and .key paths.
    • Option 3 — Plain HTTP: Port 80 only (not recommended for production).
  4. LLM Provider & Model: OpenAI, Anthropic, Azure OpenAI, or OpenRouter (plus Ollama via .env).
  5. Secrets & Sizing: Auto-generates ZITADEL_MASTERKEY, JWT_SECRET_KEY, ZITADEL_DB_PASSWORD, MinIO credentials, Grafana admin credentials, and Celery worker tuning.

Step 4: Start the Production Stack

When using external managed PostgreSQL, Redis, Qdrant, and S3 (COMPOSE_PROFILES= empty in .env):

bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

When using the bundled Postgres, Redis, Qdrant, and MinIO containers (COMPOSE_PROFILES=local-storage in .env):

bash
docker compose --profile local-storage -f docker-compose.yml -f docker-compose.prod.yml up -d

Step 5: Verify Deployment Health

bash
# Confirm all services are healthy/running (init containers should show Exited (0))
docker compose ps

# Verify Nginx health endpoint
curl -f https://app.datastrat.example.com/health

Identity & Authentication (Zitadel OIDC / SAML / SSO)

DataStrat AI ships with Zitadel v2.54.3 as its embedded OpenID Connect (OIDC) provider, isolated on its own PostgreSQL instance (zitadel_db). On first boot, zitadel_init automatically provisions the DataStrat OIDC application and writes client credentials to the shared zitadel_config volume (/zitadel-config/credentials.json).

OIDC Redirect & Reverse Proxy Headers

  • Callback URI: https://app.<domain>/api/v1/auth/oidc/callback
  • Post-Logout URI: https://app.<domain>/login
  • Nginx Buffer Sizing: Configured with proxy_buffer_size 128k and large_client_header_buffers 4 64k to accommodate large OIDC/JWT headers.
First-Login Action Required

Zitadel initializes a bootstrap human administrator (admin@datastrat.local) using ZITADEL_ADMIN_PASSWORD (defaulting to Admin123! if not overridden in .env). Sign in at https://auth.<domain> immediately after deployment to rotate this password and configure MFA.

Enterprise SSO & SAML / OIDC Federation

To federate login with your corporate Identity Provider (Microsoft Entra ID / Azure AD, Okta, Ping Identity, or Google Workspace):

  1. Log in to the Zitadel Management Console at https://auth.<domain>.
  2. Navigate to Organization → Identity Providers and add your corporate SAML 2.0 or OIDC provider.
  3. Enable auto-creation or JIT provisioning as required by your IAM policy, then assign users to DataStrat Auditor or Compliance Officer roles.

LLM & Storage Configuration

Supported LLM Providers

Both api and worker containers read the same LLM configuration from .env:

  • OpenAI: LLM_PROVIDER=openai, LLM_MODEL=gpt-4 (or gpt-4-turbo / gpt-4o).
  • Anthropic: LLM_PROVIDER=anthropic, LLM_MODEL=claude-3-5-sonnet-20240620.
  • Azure OpenAI: LLM_PROVIDER=azure, plus AZURE_OPENAI_ENDPOINT=https://<resource>.openai.azure.com/.
  • OpenRouter: LLM_PROVIDER=openrouter, LLM_BASE_URL=https://openrouter.ai/api/v1.
  • Ollama (Self-Hosted / Air-Gapped): LLM_PROVIDER=ollama, LLM_BASE_URL=http://<ollama-host>:11434.

Storage Modes: Built-in vs. Managed Cloud

When running with local-storage, persistent state is stored in Docker named volumes (postgres_data, qdrant_data, minio_data, zitadel_db_data, grafana_data). The minio_init container automatically creates the datastrat-evidence bucket with a private access policy.

For enterprise cloud deployments, configure external managed services in deploy.sh (AWS RDS, ElastiCache, Qdrant Cloud, AWS S3 / Azure Blob S3 Gateway) and omit --profile local-storage. Nginx allows evidence uploads up to 60M (client_max_body_size 60M).

Upgrading & Maintenance

Automated Upgrade Pipeline (./update.sh)

Run ./update.sh from your deployment directory to perform a 5-stage zero-config-loss upgrade:

bash
./update.sh
  1. Fetch Release: Downloads the latest datastrat-enterprise-deployment.zip from GitHub Releases.
  2. Sync Configs: Extracts updated compose and Nginx files while preserving .env and ./certs/ (re-executing itself automatically if update.sh was updated).
  3. Audit .env: Compares .env against the new .env.example and prompts for (or auto-generates) any newly added environment keys.
  4. Prune & Pull: Runs docker image prune -a -f and pulls updated container images.
  5. Restart Stack: Recreates containers cleanly with docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d.

Backups & Observability

  • Critical Host Files: Back up .env and ./certs/ to your enterprise secrets vault. Losing ZITADEL_MASTERKEY or JWT_SECRET_KEY will invalidate encrypted Zitadel state and active sessions.
  • Database & Object Backups: Snapshot managed RDS/S3 volumes, or back up Docker volumes postgres_data, zitadel_db_data, qdrant_data, and minio_data on a scheduled basis.
  • Centralized Logs: Access Grafana at https://app.<domain>/grafana/ (sign-up disabled in production). Docker json-file logs are capped at 10m × 3 files per container via docker-compose.prod.yml.

Security & Support Contact

  • Zero Cloud Telemetry: All third-party tracing tools (such as LangSmith) are strictly disabled in production builds. Prompts, evidence, and scores remain inside your VPC.
  • Sovereign Initialization: Schema migrations and seeding run in ephemeral db_init and zitadel_init containers that exit upon completion.
  • Credential Hygiene: deploy.sh enforces chmod 600 .env and restricts internal database/cache ports to 127.0.0.1.
